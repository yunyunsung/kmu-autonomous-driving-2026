# 10. 시행착오에서 배운 것

> 팀 설계 일지(본선 당일 기준 3,713줄, 140여 개 섹션)와 커밋 332개를 주제별로 다시 묶은 글입니다.
> 원문은 [`archive/`](archive/)에 그대로 있습니다. 각 항목 끝의 `§`는 원문 섹션 번호입니다.

설계 일지에는 "[중대 버그]" 표시가 붙은 항목이 6건, "실차 미검증"이라는 문구가 70번 나옵니다. 일지를 다시
읽으며 가장 크게 느낀 건, **실패의 대부분이 알고리즘이 아니라 경계에서 났다**는 점입니다. 시뮬레이터와 실차의
경계, 추론 스레드와 제어 루프의 경계, 실차 작업 사본과 저장소의 경계, 그리고 하드웨어와 소프트웨어의 경계.

## 1. 시뮬레이터는 지연과 배터리를 모른다

**상황.** 속도 15에서 손 튜닝이 한계에 부딪혀, 실제 제어 코드를 그대로 돌리는 시뮬레이터로 25개 파라미터를
탐색했습니다. 시뮬레이터상 커브 추종 오차가 7~9cm에서 1~1.6cm로 줄었습니다.

**결과.** 실차에 올리자 세 가지가 동시에 터졌습니다. 달리다 멈췄다 튀어나가고(배터리 LVC 트립), 좌회전에서
감속 없이 트랙을 이탈하고(코너 하한 ≈ 순항 속도), 직선에서 "술 취한 사람처럼" 좌우로 흔들렸습니다.

**잘못 짚은 것.** 진동의 범인으로 경로 EMA를 먼저 의심해 0.25에서 0.9까지 바꿔봤습니다. 어느 값에서도 진동이
똑같이 재현됐고, 그게 오히려 단서였습니다. EMA와 무관하다는 뜻이었으니까요.

**진짜 원인.** 조향 게인(`PP_WHEELBASE_PX`)이 검증값의 2배였습니다. 시뮬레이터는 명령이 즉시 반영된다고
가정했기 때문에 "더 정확한" 높은 게인을 골랐고, 실제 서보와 카메라 파이프라인 지연 앞에서 그 게인은 진동을
만들었습니다. 가속 한도와 코너 하한도 같은 이야기입니다. 시뮬레이터는 전류를 모르고, 인식이 몇 프레임
실패하는 상황도 모릅니다.

**배운 것.**
- 시뮬레이터 최적값은 **출발점**이지 답이 아닙니다. 최종값은 시뮬값과 상당히 다른 실차 수동 튜닝값이었습니다.
- 실차가 시뮬과 다르게 움직일 때는 시뮬이 **모델링하지 않은 것**(지연, 전류, 인식 실패)부터 의심해야 합니다.
- 탐색 공간에 물리적 제약(`corner_min < normal`, 가속 상한)을 처음부터 넣어야 합니다. 그렇지 않으면 최적화가
  제약을 깨는 쪽으로 점수를 땁니다.
- 실차에서 깨졌을 때 **게인 하나만 검증값으로 되돌리는** 수술적 접근이 프리셋 전체를 끄는 것보다 빨리
  원인을 좁혀줬습니다.

`§0.5.12~0.5.14, §2.39, §2.41` · 자세히: [04-steering-control.md](04-steering-control.md)

## 2. 조향 진동 범인 찾기

"직진에서 흔들린다"는 증상 하나에 원인이 여러 겹 쌓여 있었습니다.

| 증상 | 처음 생각 | 실제 원인 | 찾은 방법 |
|---|---|---|---|
| 직진에서 계속 한쪽으로 쏠림 | 진동 | 조향 기준점이 실제 경로 좌표계와 다른 폭으로 고정 → **평균 +24°(최대 +38°) 좌편향** | 주행 녹화 2,734장을 ROS 없이 오프라인 재생, 버그/정상 기준점으로 조향각 비교 |
| 위 수정 후에도 편향 | - | "캔버스 폭/2"도 차량 중심이 아님. BEV 4점이 좌우 비대칭(260px vs 315px) | 디버그 창의 빨간 선이 뭘 기준으로 그려지는지 질문하다 발견 |
| 직진 복귀 후 조향각이 15초 고정 | 인식 실패 | lookahead 곡률 감쇠의 **자기순환**(ld↓ → 노이즈 증폭 → 곡률↑ → ld↓) | 디버그 영상에서 offset +1.5px인데 조향 −65.7° 고정 |
| 직선에서 속도가 출렁임 | 코너 감속 과민 | 진동의 매 스윙을 **급코너로 오인** | 조향각 순간값 대신 부호 유지 EMA로 판단 |
| 고속 좌우 진동 | 경로 EMA | 조향 게인 과다 (위 1번) | EMA를 바꿔도 동일 재현 |

**배운 것.**
- **상시 편향과 프레임 간 떨림은 다른 문제입니다.** 편향이 깔린 채로 떨림만 필터로 누르려 했던 기간이 있었습니다.
  편향을 고친 뒤에야 필터를 약하게(최종 `PP_ALPHA=0.9`) 가져갈 수 있었습니다.
- **"이 선은 뭘 기준으로 그려지나?"** 같은 단순한 질문이 가장 큰 버그를 찾았습니다. 디버그 시각화가 보여주는
  값의 정의를 의심해볼 것.
- 녹화 데이터를 오프라인으로 재생하는 검증은 실차 없이도 원인을 숫자로 확정해 줬습니다.
- 진동 억제를 위해 "직진 모드/커브 모드" 이산 분기를 넣었다가 이틀 만에 통째로 걷어냈습니다. 검증되지 않은
  분기는 파라미터와 "알려진 한계"만 늘렸습니다.

`§0.5.2, §0.5.3, §0.5.9, §2.35, §2.37`

## 3. 같은 상태를 두 곳에서 들고 있으면

**사고.** 방해차량 회피 중 lookahead 목표점이 한 틱 만에 순간이동하고, 차가 그대로 벽에 부딪혔습니다.

**원인.** 경로가 두 곳에 있었습니다. 인식 모듈 내부의 `self.path`는 근접 밴드가 안 보여도 원거리 점으로 계속
갱신됐고, 제어 쪽 `self.lane_path`는 "유효할 때만 갱신" 정책으로 얼려져 있었습니다. 회피 중 장애물이 근접
밴드를 몇 프레임 가리는 동안 내부 경로만 몰래 흘러갔고, 다시 유효해지는 순간 그 누적분이 **EMA 완충 없이
한 번에** 노출됐습니다. EMA는 매 프레임 새 값에는 완충이 되지만, 얼려뒀다 한꺼번에 풀리는 값에는 아무 효과가
없었습니다.

**수정의 수정.** 내부 경로도 같은 조건으로 얼리자 이번에는 급좌회전 진입에서 경로 전체가 2초 넘게 얼어붙었습니다.
근접만 없고 원거리는 보이는 상황까지 막아버린 겁니다. 결국 "근접 필수" 조건(오프셋 계산용)과 "근접 또는
원거리"(경로용)를 분리하고, **두 곳이 같은 플래그로 얼고 풀리게** 맞췄습니다.

비슷한 구조의 버그가 하나 더 있었습니다. 회피가 시작되면 원거리 밴드만 정당하게 옆으로 밀리는데, 이상치 제거
단계가 나머지 밴드로 추세선을 그리다 보니 **아직 정상인 근접 밴드를 이상치로 판정**해 버렸습니다. 경로 시작점이
근거 없이 치우쳤고, 근접 밴드를 이상치 검사에서 보호하는 것으로 고쳤습니다.

**배운 것.**
- 비동기 시스템에서 **같은 의미의 상태를 두 군데 두면, 갱신 조건이 반드시 같아야 합니다.**
- 안전장치를 넣을 때는 그게 막는 범위가 의도보다 넓지 않은지 같이 봐야 합니다. 이 버그는 고친 당일 바로
  다음 버그를 만들었습니다.

`§2.36, §2.40, §2.44`

## 4. 조용한 실패

크래시는 금방 고칩니다. 오래 걸린 건 **에러 없이 조용히 틀린 값**이었습니다.

| 무엇이 | 어떻게 조용했나 | 얼마나 걸렸나 |
|---|---|---|
| IMU | 하드웨어 고장으로 콜백이 안 불려 `imu_yaw`가 초기값 고정. 바퀴 수가 계속 0 | 처음부터 8/6까지 |
| TensorRT | 콘 모델 엔진 빌드가 매번 실패하는데 예외 없이 456초 후 CUDA로 폴백. 노드 기동 8분 | 8/14 |
| ultralytics export | ONNX export가 `nms=True`를 경고 없이 무시 | 우회 코드를 만든 다음 날 원인 발견 |
| 테스트 플래그 | 회피 기동을 꺼둔(`TEST_DISABLE_B2_B3`) 채로 회피 대기 속도 제한은 계속 동작 → **속도가 40초 넘게 5에 고정** | 8/18, 녹화 프레임 분석 |
| 추론 스레드 | 결과가 안 바뀌는 게 "느려서"인지 "죽어서"인지 구분 불가 | 8/11 |
| 코너 감속 | 그리드서치 프리셋의 코너 하한이 순항 속도보다 커서 감속이 꺼진 채 최고점 | 8/18 |

**팀이 정착시킨 패턴.** 센서와 추론 결과마다 마지막 갱신 시각(`_*_t`)을 두고, 일정 시간(`*_STALE_SEC`) 이상
갱신이 없으면 감속합니다. 콜백이 안 불리는 건 예외가 아니라 "값이 안 움직이는 것"으로만 드러나기 때문입니다.

**배운 것.**
- 폴백은 편하지만 **실패를 숨깁니다.** 어떤 프로바이더로 로드됐는지, 어떤 백엔드로 폴백했는지를 기동 로그에
  반드시 찍어야 합니다.
- 테스트용 플래그는 다른 로직과 **함께 꺼지는지** 확인해야 합니다. 한쪽만 꺼진 채 다른 쪽이 계속 돌면
  아무도 의도하지 않은 상태가 됩니다.

`§2.24, §2.31, §2.43, §2.59, §8.4`

## 5. 단순한 쪽이 이겼다

| 미션 | 정교하게 만든 것 | 본선에서 쓴 것 |
|---|---|---|
| 라바콘 | 보로노이 → 순번 짝짓기 → 최근접 이웃 → 박스 스택 (하루에 4번 교체) | **일반 차선 주행** + 진입 킥 + 라이다 push 안전판 |
| 장애물 | Hybrid A*, TargetPassing 옆차선 기동, avoid-hold | **da를 잘라** 차선 주행이 알아서 피하게 |
| 신호등 | HSV, 배경판 자동 크롭, FRST, Hough 튜닝, 3중 필터 | **YOLO 단일 모델** + 디바운스 |
| 지름길 | 오픈루프 90°, IMU yaw 폐루프, 점선 카운터 | 라이다 기둥쌍 + **완만한 램프** |
| 조향 | LQR, Stanley, 직진/커브 이중 모드 | **Pure Pursuit 하나** |

다섯 미션 모두 같은 방향으로 수렴했습니다. 가장 많이 검증된 경로(da 세그멘테이션 + Pure Pursuit)에 얹을 수
있으면 얹었습니다. 세그멘테이션 모델이 콘과 장애물을 이미 "도로가 아닌 것"으로 보고 있었기 때문에, 전용
회피 경로를 따로 만드는 것보다 **da를 조금 고쳐주는 게** 실차에서 더 안정적이었습니다.

장애물 회피에서 lookahead를 늘리는 안을 코드 없이 수식만으로 버린 것도 기억에 남습니다. 곡률 ≈ 2·dx/ld²이라
멀리 볼수록 같은 횡편차가 희석됩니다. 실차에서 시험해보기 전에 계산으로 걸러낼 수 있었던 사례입니다.

`§2.48~2.51, §3.1~3.5, §1.1~1.18`

## 6. 규칙으로 알 수 있는 건 규칙으로, 단 가정은 적어둘 것

- **T자 출구**: 반시계 트랙이라 지름길 출구에서는 항상 좌회전입니다. 차선 인식은 이 규칙을 모르고 양쪽 다 도로로
  봅니다. 램프 완료 후 5.5m에서 고정 조향을 거는 것으로 해결했습니다.
- **B2 → B3 순서**: 라이다로는 고정장애물과 방해차량이 비슷하게 보입니다. 트랙 순서를 이용해 B2 통과 후 3초간은
  무엇이든 B2로 취급합니다.

그런데 이 순서 가정은 8/21에 반대로 뒤집었다가 8/22에 실제 트랙과 맞지 않아 원복했습니다. **가정이 틀리면
오분류 가드가 반대로 작동**합니다. 규칙 기반 처리는 그 규칙이 무엇을 가정하는지 "알려진 한계"에 반드시 적어
두고, 대회 당일 확인 목록에 넣어야 합니다.

`§5.2, §5.4, §5.5, §1.19o`

## 7. 하드웨어 문제는 소프트웨어로 덮을 수 없다

| 증상 | 소프트웨어 대응 | 결과 |
|---|---|---|
| 가속 중 순간 정지 | 가속 램프 완화 | 완화됨. 단, 시뮬 프리셋이 다시 키우자 재발 |
| 출발 초반 툭툭 끊김 | 램프 완화 → 첫 틱 점프(`SPEED_KICK_START`) | **효과 없음.** 출발 성공률이 오히려 떨어진 세션도 |
| 라이다 각도 오프셋 드리프트 의심 | 측정 도구 제작 | 좌우 판정 전체에 영향이 커서 대회 전 반영 못 함 |
| 라이다 포인트 수 가정(360 vs 500) | 측정 도구에서만 수정 | 주행 코드 미반영 |
| VESC가 5~11% 높게 보고 | 줄자 실측 회귀를 기준으로 | 게인 재보정은 미결정 |

출발 문제는 두 가설을 소프트웨어로 다 시도한 뒤에야 배터리 내부저항, ESC 보호 임계값, 커넥터 쪽을 의심하게
됐습니다. **정상 배터리팩으로 A/B 비교**를 먼저 했다면 며칠을 아낄 수 있었을 겁니다.

`§7.1, §7.2, §2.30, §10`

## 8. 원인을 찾게 해준 도구들

설계 일지에서 진단이 빨랐던 순간에는 거의 항상 전용 도구가 있었습니다.

- **오프라인 재생**: 주행 녹화 프레임을 ROS 없이 인지·제어 모듈에 직접 넣어 조향각을 비교. 좌편향 24°를 숫자로 확정.
- **휴대폰 영상 프레임 분석**: 팀 단톡방에 올라온 주행 영상을 `ffmpeg`로 프레임 단위로 뽑아, 디버그 창 숫자가
  튀는 순간과 사고 시점을 맞춤. 벽 충돌과 "속도 5 고정" 원인이 여기서 나왔습니다.
- **신호등 오프라인 검증기**: 녹화 2,262프레임에 알고리즘을 돌려 오탐을 세는 스크립트. 사람이 디바운스를 통과하는
  사례를 찾았습니다.
- **측정 전용 디버그 창**: YOLO 박스 면적, 라이다-카메라 오프셋, VESC 생존 상태를 따로 띄우는 창. 임계값을 감이
  아니라 측정으로 정할 수 있었습니다.

반대로 디버그 표시가 착시를 만든 경우도 있습니다. 좌회전 신호가 "확정 안 된다"는 보고의 상당수는 상태 전환
순간 카운터가 리셋되며 생긴 **표시상의 착시**였고, FSM은 이미 반응한 뒤였습니다.

## 9. 일하는 방식

- **실측 / 설계값 / 실차 미검증을 구분해 적기.** 팀이 가장 잘 지킨 원칙입니다. 덕분에 "이 값은 믿어도 되나"를
  매번 다시 물을 필요가 없었습니다.
- **살아있는 설계 일지.** 날짜, 원인, 수정, 남은 한계를 적는 형식이 일관돼서 한 달 뒤에도 경위를 따라갈 수
  있었습니다. 다만 3,700줄이 되자 아무도 처음부터 읽지 못했고, 대회 후 압축되면서 이력이 git 속으로
  들어갔습니다. **현재 동작 문서와 시행착오 기록을 처음부터 분리**했다면 둘 다 살릴 수 있었을 겁니다. 이
  저장소가 그 분리를 뒤늦게 한 결과물입니다.
- **한 대의 차, 여러 명, 공용 계정.** 실차 작업 사본과 저장소를 파일 복사로 동기화하다 보니 고친 버그가 다른
  커밋에 섞여 되돌아간 일이 여러 번 있었습니다(8/10, 8/13, 8/17). 커밋 계정도 실제 작업자와 맞지 않았습니다.
- **"★반드시 원복★" 플래그.** 격리 테스트용 시작 상태와 강제 스위치가 여러 번 켜진 채 남을 뻔했습니다.
  기동 시 테스트 플래그를 검사하는 레이스 모드 체크가 있었다면 좋았을 겁니다.
