# 06. Jetson 이식과 TensorRT 최적화

> 조향 튜닝과 함께 제가 가장 오래 매달린 영역입니다. 모델을 학습하는 것과, 그 모델을 차 위에서 20Hz 제어
> 루프에 맞춰 돌리는 건 완전히 다른 문제였습니다.

## 왜 Jetson이 필요했나

자이카 Y모델의 기본 컴퓨터는 AMD Ryzen 7 5700U에 내장 그래픽뿐이고 ROCm도 지원되지 않아, 추론은 CPU로만
가능했습니다. 차선 인식을 TwinLiteNet+로 바꾸자 **CPU 추론이 약 10.8fps**에 그쳤고, 20Hz 제어 루프의 절반
수준이었습니다. 여기에 YOLO 모델까지 올릴 계획이었기 때문에 8월 중순 컴퓨팅 보드를
**reComputer Super J4012(Jetson Orin NX 16GB, JetPack 6)** 로 교체했습니다.

| 환경 | TwinLiteNet+ | 비고 |
|---|---|---|
| Ryzen 7 5700U, CPU | 약 10.8fps | 기본 차량 |
| 개발 PC, CUDA EP | 약 5.7fps | TensorRT 빌드가 안 끝나 임시로 쓴 설정 |
| **Jetson Orin NX, TensorRT FP16** | **약 18fps** | 본선 |
| Jetson Orin NX, YOLO | 약 25fps | |

보드 교체 체크리스트(ROS2·Docker·udev 재설정, Jetson용 onnxruntime 휠 등)는
`src/track_drive/track_drive/JETSON_SETUP.md`에 있습니다.

## 추론 구조

- 모든 모델은 **ONNX Runtime**으로 실행합니다. Jetson에서는 일반 pip 버전이 아니라 CUDA·TensorRT
  실행 프로바이더가 포함된 Jetson용 휠을 설치해야 합니다.
- 각 모델은 프로바이더 우선순위를 따로 가집니다. 본선 기준:

  | 모델 | 프로바이더 | 이유 |
  |---|---|---|
  | TwinLiteNet+ | TensorRT(FP16, 엔진 캐시) → CUDA → CPU | 매 프레임 도는 가장 무거운 모델 |
  | YOLO 콘 · 방해차량 · 신호등 | CUDA → CPU | 아래 NMS 문제 이후 안전한 쪽 선택 |

- 추론은 모델마다 **백그라운드 스레드**에서 돌고, 제어 루프는 최신 결과만 가져갑니다. ONNX Runtime 스레드
  수는 2개로 제한했습니다. Jetson 코어 수가 적어 ROS2 콜백 스레드와 경쟁하기 때문입니다.
- YOLO 3종은 동시에 돌리지 않고, **현재 미션 단계에 필요한 모델 하나만** 켭니다
  ([02-system-architecture.md](02-system-architecture.md#모델-단계별-가동)). 레이스 모드에서는 디버그 창도
  모두 꺼서 GPU 부하를 줄였습니다.

## 부딪힌 문제들

### 1. 노드가 켜지는 데 8분 — NMS 레이어와 TensorRT

라바콘 YOLO를 붙이자 노드가 기동할 때마다 7~8분씩 멈췄습니다.

- **원인**: `cone_best_n.onnx`는 `nms=True`로 export되어 그래프 안에 `NonMaxSuppression` 레이어가
  있었습니다. TensorRT는 이 레이어의 빈 텐서를 처리하지 못해 엔진 빌드가 **항상 실패**합니다
  (`TRT-16198`).
- **더 나빴던 점**: ONNX Runtime은 이 실패를 예외로 올리지 않고, 약 456초를 쓴 뒤 **조용히 CUDA로
  폴백**했습니다. 에러 로그가 없으니 "왜 느린지"를 찾는 데 시간이 걸렸습니다.
- **조치**: 이 모델은 프로바이더에서 TensorRT를 빼고 CUDA로 직행. 근본적으로는 검출기 생성자가 노드
  `__init__`에서 동기 호출되는 구조라, 다른 모델에서 같은 일이 생기면 재발할 수 있습니다.

### 2. 엔진 캐시가 영영 안 만들어짐

TwinLiteNet+를 v1.2.0으로 바꾸자 차선 인식이 아예 안 되는 것처럼 보였습니다.

- **원인**: 새 모델의 TensorRT 첫 엔진 빌드가 4분 이상 걸렸는데, 실차 테스트 중에는 노드를 수시로
  재시작하다 보니 **빌드가 끝나기 전에 매번 죽였습니다.** 캐시가 한 번도 완성되지 않으니 다음 실행도
  처음부터 다시 빌드했습니다.
- **임시 조치**: CUDA로 전환해 일단 테스트를 이어감.
- **결말**: 6일 뒤 TensorRT를 다시 켜보니 즉시 로드됐습니다. 그날 어느 실행이 백그라운드에서 끝까지 완주해
  `trt_cache/`에 엔진이 남아 있었던 겁니다.
- **교훈**: TensorRT 엔진 빌드는 **배포 절차의 한 단계**로 분리해, 대회 전에 한 번 끝까지 돌려 캐시를
  만들어 두어야 합니다. 캐시는 GPU·드라이버마다 다르므로 git에는 올리지 않습니다.

### 3. `nms=True`를 줬는데 NMS가 없다

방해차량 전용 모델을 만들면서 처음부터 `nms=False`로 export해 TensorRT 문제를 피하고, 대신 raw 출력
`[1, 5, 8400]`을 직접 디코딩하고 `cv2.dnn.NMSBoxes`로 NMS를 하는 코드를 붙였습니다.

그런데 나중에 원인을 다시 파보니, **ultralytics 8.3.0의 ONNX export는 `nms` 인자를 아예 참조하지 않았습니다.**
그 옵션은 CoreML export 전용이었고, ONNX에는 경고 없이 무시됐습니다. 그래서 `forward()` 안에
`torchvision.ops.batched_nms`를 직접 넣은 커스텀 export 스크립트로 방해차량·신호등 모델을 다시 내보냈고,
출력이 `[1, N, 6]`(x1, y1, x2, y2, conf, cls)로 고정되면서 수동 디코딩 코드를 다시 걷어냈습니다.
가중치는 그대로 두고 export 방식만 바꾼 버전이 v1.2.0입니다.

### 4. 네 모델을 한 보드에

TwinLiteNet+ 18fps, YOLO 25fps는 **각각 단독일 때** 숫자입니다. 넷을 동시에 돌리면 20Hz를 지킬 수 없었습니다.
그래서 위의 단계별 가동을 도입했고, 라바콘 구간처럼 콘이 카메라를 가려 추론이 무의미한 구간에서는 YOLO를
아예 껐습니다.

추론이 비동기라 생긴 문제도 있었습니다. 제어 루프 입장에서 "결과가 안 바뀜"이 **추론이 느려서**인지
**스레드가 죽어서**인지 구분이 안 됐습니다. 결과마다 시퀀스 번호를 붙이고, 일정 시간(2초) 이상 갱신이 없으면
감속하도록 했습니다.

## 정리

| 하고 싶었던 것 | 실제로 필요했던 것 |
|---|---|
| 모델을 TensorRT로 빠르게 | export 그래프에 TensorRT가 못 다루는 레이어가 없는지 확인 |
| 실패하면 에러가 날 것 | 실패해도 조용히 폴백하므로 **어떤 프로바이더로 로드됐는지 기동 로그에 출력** |
| 실행하면 빠를 것 | 첫 빌드는 수 분, **캐시를 미리 만들어 두는 배포 단계** |
| 모델별 fps가 충분 | 동시 실행 시 GPU를 나눠 쓰므로 **필요한 모델만 켜는 스케줄링** |

다음에 한다면 INT8 양자화(캘리브레이션 데이터셋 별도 확보)와, 추론 시간을 제어 루프 로그에 같이 남기는
프로파일링부터 넣겠습니다. 이번엔 fps를 모델 단독으로만 쟀고, 실제 주행 중 지연이 얼마였는지는 기록이
부족했습니다.
